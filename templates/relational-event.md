# Relational event authoring form

Use this form to create a JSON record matching `schemas/relational-memory.schema.json` under `memory/relational/`. This form is not a memory and contains no real experience. Do not leave placeholders or invent missing evidence. If there is no meaningful event, keep an optional transient note instead.

Record:
- ID and proposing member; at least two configured participants (Santiago may be one).
- Existing project slug and event date.
- Status: proposed initially; distinguish verification from adoption.
- Relevant event, with bounded factual description.
- Each participant's attributed interpretation and acknowledgment: pending, confirmed, or disputed.
- Evidence locators and what each supports; inspect local files and remote sources.
- Tension, positive development, conflict repair, or mixed outcome.
- Affected relationship qualities separately, with scope, change, evidence references, and limitations.
- What concretely changes in future collaboration.
- Qualitative confidence, limitations, and contrary evidence.
- Review status, reviewer, date, decision, declared evidence references, reasoning, and independence.
- Whether the event should motivate an identity proposal and why; no active identity change follows from this field.
- Supersession/deprecation references and reason where applicable.

Manual review must check that interpretations refer to actual participants, participant responses are genuine, IDs are unique, projects/evidence/memories exist, review evidence is declared, the reviewer is independent, and unresolved objections remain visible. Ordinal confidence is not proof or an automatic promotion threshold.

Verified status requires independent evidence review; adopted status additionally requires an explicit scoped adoption decision. A commit alone establishes neither. Pending interpretations remain pending; unresolved disputed interpretations block adoption of a shared interpretation. Pair-specific commitments require both participants' review. A record involving Santiago's preferences requires his explicit confirmation.

For identity evolution, translate relevant adopted events into valid existing memory records, preserving event provenance and status, then propose the normal versioned amendment. The original relational event must not be silently recast as verified technical evidence.
